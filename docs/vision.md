# create-ama-plugin — Architecture & Vision

> Read this before touching #1. This doc exists so an implementing agent
> has everything needed without guessing at conventions or re-deriving
> decisions already made elsewhere in the mesh.

## Why this repo exists

This is the `bun create`-style scaffold for any new Orchestrator plugin
in the mesh (connectors, Agent Manager, future console panels). It is
the seed of a WordPress-like extensibility model: the Orchestrator is
core, Verdaccio (private now, able to front public npm later without a
rewrite) is the plugin registry, and this repo is the plugin boilerplate
generator.

Originally scoped as `ama-shared-context#183`. Moved here on 2026-09-10,
once this repo existed, so the tracking issue lives with the code
instead of sitting cross-repo — the same fix already applied to
`ama-plugin-contract#1` / `ama-shared-context#182`.

## Two sources to draw from — do not conflate them

This repo needs conventions from **two different existing repos**, each
for a different reason. Pulling the wrong thing from the wrong source is
the most likely way this goes off track.

**From `ama-bun-ts-template` (`Ask-Me-Anything-dot-work/ama-bun-ts-template`)
— bootstrap/scaffold conventions:**
- `AGENTS.md` — pattern for repo-specific coding-agent instructions.
- `package.json`, `tsconfig.json`, `eslint.config.mjs`, `knip.config.ts`,
  `bunfig.toml` — base tooling config for any new `ama-*` Bun/TS repo.
- `src/`, `tests/` folder layout.
- This template is intentionally lean — it does **not** include
  `.releaserc.json` or `.github/workflows/`. Do not assume it has a
  publish pipeline; it doesn't.

**From `ama-mcp-atlassian` (`Ask-Me-Anything-dot-work/ama-mcp-atlassian`)
— publish/release conventions:**
- `.github/workflows/ci.yml` and `release.yml` — copy and adapt.
- `.releaserc.json` — semantic-release config.
- `commitlint.config.ts` — conventional-commit enforcement, required for
  semantic-release to compute version bumps correctly.
- This is the current reference implementation of a small, standalone,
  publicly-published `ama-*` package with a working CI/release pipeline.

Read both repos directly, file by file. Do not fabricate CI/release YAML
from general knowledge — the mesh's actual pipeline conventions are what
matter here, not generic semantic-release boilerplate.

## What the generated project must look like

The scaffold's job is to produce a new plugin repo that:

1. Depends on `ama-plugin-contract` (public npm, semver-ranged) for
   `PluginBridge`, `IncomingEvent`, `PluginManifest`, `ConsolePanel`,
   `MockBridge`. See `ama-plugin-contract#1` and that repo's
   `docs/vision.md` for the exact interface shapes — do not
   re-implement or duplicate these types locally.
2. Includes a stub implementing `OrchestratorPlugin`:
   ```typescript
   interface OrchestratorPlugin {
     id: string
     onInstall?(bridge: PluginBridge): Promise<void>
     onStart(bridge: PluginBridge): Promise<void>
     onStop(): Promise<void>
   }
   ```
3. Includes at least one passing test written against `MockBridge` out
   of the box — the generated project should be green on `bun test`
   immediately after scaffolding, with zero manual setup.
4. Optionally scaffolds a console panel matching the `ConsolePanel`
   contract, if the user opts in during the interactive prompt.
5. Ships a `bun run publish` script that targets Verdaccio
   (`http://verdaccio.homelab`) by default, with a config flag to switch
   to the public npm registry later — do not hardcode Verdaccio as the
   only option.

## The interactive scaffold itself

`bun create ama-plugin <name>`-style flow. At minimum, prompt for:
- Plugin id (kebab-case, used as npm package name)
- `provides` value (open/generic, per the widened type in
  `ama-plugin-contract`, not the old `('connector')[]` union)
- Console panel: yes/no
- Migrations: yes/no

Keep the prompt set small. This is meant to lower the barrier to writing
a new plugin, not introduce a long wizard.

## `provenance`/`source` field

The manifest generated by the scaffold should include a
`provenance`/`source` field, reserved and unused for now. It exists so
that once the mesh's plugin registry is public, plugin authors and
consumers can eventually verify where a plugin came from. Do not build
any verification logic against it yet — just reserve the field.

## Breaking-change awareness

This repo pins `ama-plugin-contract` as a semver range specifically so
that a breaking change in the contract package fails the generated
project's install/build loudly, rather than silently drifting out of
sync. Do not loosen this pin to `*` or `latest` for convenience.

## Downstream consumers to keep in mind

- Any future plugin author, human or agent, using
  `bun create ama-plugin` as their starting point — this is the
  intended primary consumer.
- Agent Manager (planned) — likely the first real plugin built using
  this scaffold, and the first to need a non-`'connector'` `provides`
  value.
